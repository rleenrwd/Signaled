# Signaled MVP API Contract

**Status:** Approved for MVP  
**Date:** September 27, 2026  
**API base:** `/api/v1`  
**Purpose:** Specify the HTTP operations and externally visible behavior needed to build the approved Signaled MVP.

## 1. Authority and scope

This contract implements the [MVP requirements](../requirements/signaled-mvp-requirements.md), [user flows](../design/signaled-user-flows.md), [architecture](signaled-mvp-architecture.md), and [ERD/data model](signaled-mvp-data-model.md). It covers the web interface and the approved external event-ingestion integration. It does not create extra product features because a mockup happens to display them. The later security design maps capability names to roles, defines record visibility, selects the identity provider, and approves file/configuration policies; those choices cannot broaden this contract silently.

All paths below are relative to `/api/v1`. These are the MVP operation shapes; an OpenAPI description and implementation DTOs must conform to them. Fields labeled **required** are required for that command, subject to the conditional rules stated here. A `?` denotes optional or nullable. Unknown JSON members are rejected on commands that change data, preventing ignored security-sensitive input. Server-computed IDs, actors, timestamps, statuses, and audit fields are never trusted from client payloads.

## 2. Common HTTP rules

| Concern | Contract |
| --- | --- |
| Authentication | All routes require an authenticated, active identity except deployment health checks. Human routes use the provider flow defined by security design; `/integrations/*` uses an approved service identity. A disabled user or revoked service identity cannot perform new actions. |
| Authorization | Every operation checks its capability and the requested record scope on the server. List, count, search, and file results apply the same scope. `GET /me` describes current allowed capabilities without declaring access to an unexamined record. |
| IDs | Route IDs are UUIDs; `eventNumber`/`caseNumber` are immutable display identifiers. Read models include both. Clients do not choose either. |
| Dates | ISO 8601 timestamps with offset in requests; responses use UTC `Z`. `occurredAt` is the time the event happened; `createdAt`, `submittedAt`, `ingestedAt`, and audit timestamps are server-controlled. |
| JSON | Requests and responses use `application/json`, UTF-8, camelCase. File uploads use `multipart/form-data`; downloads provide a safe content type and attachment disposition. |
| Success | Create returns `201 Created` with resource and `Location`; accepted asynchronous intake returns `202 Accepted` with operation location; successful mutation returns `200` with updated resource, or `204` if no representation; list returns `200`. No success response may precede durable commit of the claimed state. |
| Concurrency | Mutable resources carry a strong opaque `ETag`. Mutating an existing resource requires `If-Match` and returns a new ETag. Missing precondition → `428`; stale version → `412`. An action on an unchanged but invalid lifecycle state → `409`. Child action endpoints use the parent ETag where they affect parent state; a successful child action advances and returns that parent ETag. |
| Idempotency | External intake uses source identity/system/key and a payload hash. Retry of the same payload returns the existing operation, including its outcome; conflicting payload on the same key → `409`. Other create commands accept `Idempotency-Key` for safe client retry; repeated same key/body returns the original result and a changed body conflicts. Keys are scoped to identity and operation and stored for the operational period defined later. |
| Pagination | Lists use `pageSize` (default 25, maximum 100) and opaque `cursor?`. Response: `items`, `nextCursor?`, `hasMore`; `totalCount?` is included only where calculated after access scoping. Stable server ordering includes a unique ID tie-breaker. Invalid cursor/filter → `400`. No unbounded export endpoint. |
| Sorting/filtering | Only allowlisted field names and operators listed on each route are accepted; unknown sort/filter keys → `400`. Date ranges use inclusive `from` and exclusive `to`; `from < to`. |
| Traceability | `X-Correlation-ID` may be supplied as a safe bounded value or generated by Signaled; the response returns it. It propagates to outbox, Service Bus, worker, audit where applicable, and telemetry. No secret or full investigative narrative is placed in headers/logs. |
| Errors | Errors use the envelope in §2.1. Authentication failure → `401`; authenticated but insufficient capability → `403`; a direct record outside visibility scope → `404` indistinguishable from absent; validation → `400` or `422`; conflicts/preconditions as above; unavailable dependency → `503`. |

### 2.1 Error envelope

```json
{
  "type": "https://signaled.example/problems/validation",
  "title": "Request validation failed",
  "status": 422,
  "code": "validation_failed",
  "correlationId": "6db91c9a-6984-4d06-ac08-91d9c58a3050",
  "errors": { "occurredAt": ["An occurrence time is required."] }
}
```

The example domain is illustrative, not a deployed URL. The envelope uses a stable machine `code`, human-safe `title`, HTTP `status`, correlation ID, and optional field `errors`. `403` is appropriate for a known capability denial; `404` for a record that must not be disclosed. Never return a secret, stack trace, SQL/Blob path, raw token, unauthorized record metadata, or internal search candidate. Relevant codes include `validation_failed`, `authentication_required`, `access_denied`, `not_found`, `invalid_transition`, `review_locked`, `conflict`, `precondition_required`, `precondition_failed`, `file_unavailable`, `dependency_unavailable`, `idempotency_conflict`, and `processing_failed`. Only stable codes may drive UI logic; prose can change.

## 3. Principal read models

| Model | Minimum externally visible fields | Notes |
| --- | --- | --- |
| `EventSummary` | `id`, `eventNumber`, `title`, `status`, `sourceType`, `occurredAt`, `submittedAt?`, `createdBy` safe summary, `linkedCaseCount` | Restricted to permitted records and visible links. No original narrative in a list unless explicitly approved. |
| `EventDetail` | summary plus `description`, `createdAt`, `ingestedAt?`, `sourceSystem?`, `location?`, `category?`, `attachments`, `followUpRequests`, `currentTriageDecision?`, `linkedCases`, `etag` | Original submitted fields are stable; subsequent follow-up and corrections are separate entries. |
| `CaseSummary` | `id`, `caseNumber`, `title`, `status`, `priority`, `dueAt?`, `currentInvestigator?`, `updatedAt`, `originEventId` | Scoping precedes counts and pagination. |
| `CaseDetail` | summary plus `synopsis`, `createdAt`, `closedAt?`, `linkedEvents`, `evidence`, `findings`, `reviewCycle`, `etag` | Synopsis is full in API; UI may collapse it with “Read more.” |
| `EvidenceMetadata` | `id`, `parentType`, `parentId`, `originalName`, `contentType`, `sizeBytes`, `classification?`, `description?`, `status`, `uploadedBy`, `uploadedAt?`, `etag` | No Blob reference or signed URL in list/detail response. |
| `ActivityEntry` | `id`, `kind`, `actionCode`, `occurredAt`, `actor`, `summary`, `recordId`, `correlationId?` | Combines permitted business timeline/audit entries without silently changing their authoritative source. |
| `IngestionOperation` | `id`, `status`, `acceptedAt`, `completedAt?`, `eventId?`, `failureCode?`, `correlationId`, `etag` | `Accepted`/`Processing` do not claim an event exists. Failure detail is restricted by identity and role. ETag protects correction/replay commands. |

Collection routes return the appropriate summary model; detail routes may include selected nested summaries but remain bounded. A nested collection that can grow without limit has its own paginated route. Audit and history views use a fixed chronological order with a stable ID tie-breaker.

## 4. Event creation, follow-up, and triage

| Method and path | Body/query and response | Guard and effect |
| --- | --- | --- |
| `POST /events` | Body `title?`, `description?`, `occurredAt?`, `sourceType?`, `category?`, `location?`; `201 EventDetail` (`Draft`) | Authorized Contributor creates own draft; incomplete data is allowed here. Server sets creator and timestamps. |
| `GET /events?status&sourceType&from&to&sort&cursor&pageSize` | `200 EventSummary[]` page | Permitted events only; contributor's own-event minimum is preserved subject to approved restrictions. |
| `GET /events/{id}` | `200 EventDetail` + ETag | Scope checked; submitted original remains available alongside later additions. |
| `PATCH /events/{id}` | Allowed draft fields above; `200 EventDetail` | Creator or otherwise permitted editor, `Draft` only; `If-Match` required. Partial patch changes only supplied fields. |
| `POST /events/{id}/submit` | Empty body; `200 EventDetail` | `Draft` only. Require valid title, description, occurrence time, and any fields approved for submission. Atomically set submitted state/time and audit. |
| `POST /events/{id}/amendments` | `{ "fieldName": "...", "newValue": "...", "reason": "..." }`; `201 EventAmendment` | Separately authorized correction to an allowlisted submitted field. Append amendment/audit with prior value; never overwrite original submitted content. `If-Match`. |
| `GET /events/{id}/activity?cursor&pageSize` | `200 ActivityEntry[]` page | Includes status, follow-up, triage, corrections, link activity as permitted. |
| `GET /events/{id}/follow-up-requests?cursor&pageSize` | `200` page of requests/responses | Status and requestor/responder/timestamps visible to authorized Contributor and investigation personnel. |
| `POST /events/{id}/follow-up-requests` | `{ "prompt": "..." }`; `201 FollowUpRequest` | Authorized investigation personnel, submitted event; required nonblank prompt. Status/history/audit updated atomically. |
| `POST /events/{id}/follow-up-requests/{requestId}/responses` | Multipart `responseText` required, `files[]` optional; `201 FollowUpResponse` | Authorized Contributor responding to open request on own permitted event. Stage/validate all files before response becomes complete; response/files/status/audit commit together after storage succeeds. A partial file failure cannot create a completed response. |
| `POST /events/{id}/follow-up-requests/{requestId}/close` | `{ "reason?": "..." }`; `200 FollowUpRequest` | Authorized investigation personnel, request Open or Responded; append status/audit. `If-Match` on request. Closing does not erase the response. |
| `GET /events/{id}/triage-decisions?cursor&pageSize` | `200` page of decisions and corrections | Authorized historical view, including prior outcome, rationale, actor, and time; no discarded decision. |
| `POST /events/{id}/triage-decisions` | `{ "outcome": "OpenCase" | "NoCase", "rationale": "..." }`; `201 TriageDecision` | Authorized Investigator; event submitted, no pending blocking follow-up, rationale required. `NoCase` retains event. `OpenCase` puts event in `EscalationPending`, not a case yet. Requires parent ETag. |
| `POST /events/{id}/triage-decisions/{decisionId}/corrections` | Same outcome/rationale plus `correctionReason`; `201 TriageDecision` | Separately authorized correction; append decision, preserve original. Guard against contradiction with an existing origin case; if linked, correction cannot silently unlink/erase it. |

Example draft and submission:

```http
POST /api/v1/events
Content-Type: application/json
Idempotency-Key: 9f7bb2ab-f878-4505-981a-c8dbc1494258

{"title":"Equipment inspection discrepancy","description":"Observed during inspection.","occurredAt":"2026-09-22T10:35:00-07:00","sourceType":"FacilityReport"}
```

The resulting draft has server-generated `id`, `eventNumber`, creator, `status: "Draft"`, and ETag. The submit call uses that ETag. An optional browser “Save response draft” control may hold local unsent text, but no server-side follow-up draft endpoint is promised by the approved requirements.

## 5. Case investigation and Supervisor review

| Method and path | Body/query and response | Guard and effect |
| --- | --- | --- |
| `POST /events/{id}/cases` | `{ "title": "...", "synopsis": "...", "priority": "High", "dueAt": "..." }`; `201 CaseDetail` | Authorized Investigator, current `OpenCase` triage, no existing origin case for this decision. Case, origin link, `AwaitingAssignment`, status changes, and audit commit atomically. `If-Match` on event. |
| `GET /cases?view&status&priority&investigatorId&from&to&sort&cursor&pageSize` | `200 CaseSummary[]` page | `view` supports `mine`, `team`, `permitted` when allowed. Scope and permission before filtering/counts. |
| `GET /cases/{id}` | `200 CaseDetail` + ETag | Full permitted case summary and relationships; no arbitrary unbounded nested history. |
| `GET /cases/{id}/activity?cursor&pageSize` | `200 ActivityEntry[]` page | Status, assignment, links, evidence, notes, finding/review events, closures/reopenings. |
| `GET /cases/{id}/assignments?cursor&pageSize` | `200` page of assignment intervals | Authorized viewers can reconstruct owner, assigner, start/end, and reason where permitted. |
| `GET /cases/{id}/review-decisions?cursor&pageSize` | `200` page of decisions | Authorized viewers can reconstruct each review cycle, return/closure/reopen reason, Supervisor, and time. |
| `GET /cases/{id}/linked-events?cursor&pageSize` | `200` permitted `EventSummary` + link kind/time | Do not expose linked events caller cannot see under the final visibility policy. |
| `POST /cases/{id}/linked-events` | `{ "eventId": "uuid", "reason?": "..." }`; `201 Link` | Authorized Investigator, permitted case and event, editable case state. Duplicate active pair → `409`; `If-Match` on case; append link/audit. |
| `DELETE /cases/{id}/linked-events/{linkId}` | `{ "reason": "..." }`; `204` | Authorized unlink, related active link only. Deactivate with actor/time/reason; no event/case deletion. Origin cannot be unlinked. `If-Match`. |
| `PUT /cases/{id}/assignment` | `{ "investigatorUserId": "uuid", "reason?": "..." }`; `200 CaseDetail` | Supervisor permission, active eligible Investigator. Close previous interval, create new interval, update projection/audit atomically. `If-Match`. |
| `PATCH /cases/{id}/management` | `{ "priority?": "Low|Medium|High", "dueAt?": "...", "synopsis?": "..." }`; `200 CaseDetail` | Field-level authorized editor; priority/due changes preserve `CasePriorityChange`. Read-only/review-lock guards apply; `If-Match`. Explicit null `dueAt` clears it if permitted. |
| `GET /cases/{id}/notes?cursor&pageSize` | `200` page of note summaries | Include current revision and author/time, permitted history via detail route. |
| `POST /cases/{id}/notes` | `{ "body": "..." }`; `201 Note` | Permitted Investigator in editable investigation state; append initial revision and audit. `If-Match` on case. |
| `GET /cases/{id}/notes/{noteId}` | `200 Note` with revisions | Scoped case read; prior revisions visible only to authorized viewers. |
| `POST /cases/{id}/notes/{noteId}/revisions` | `{ "body?": "...", "changeKind": "Correct|Remove", "reason": "..." }`; `201 NoteRevision` | Correct/remove only with allowed capability, nonblank reason, editable state and `If-Match` on case. Removal is a tombstone. |
| `GET /cases/{id}/findings?cursor&pageSize` | `200` page of findings | Investigator/Supervisor/Auditor within scope; no mutation by Auditor. |
| `POST /cases/{id}/findings` | `{ "conclusion": "...", "rationale": "..." }`; `201 Finding` | Authorized Investigator, editable state; both required. `If-Match`. |
| `GET /cases/{id}/findings/{findingId}` | `200 Finding` with revisions | Scoped read; earlier revisions retained. |
| `POST /cases/{id}/findings/{findingId}/revisions` | `{ "conclusion?": "...", "rationale?": "...", "changeKind": "Correct|Remove", "reason": "..." }`; `201 FindingRevision` | Guard state/capability; preserve predecessor; `If-Match`. |
| `GET /cases/{id}/review-readiness` | `{ "ready": false, "missing": ["..."], "reviewCycle": 1 }` | Current rules from requirements/data model; no automated compliance verdict. |
| `POST /cases/{id}/submit-for-review` | Empty body; `200 CaseDetail` | Assigned/permitted Investigator. Completeness validation; moves to `AwaitingReview`, increments review cycle, freezes review-controlled edits, audits. `If-Match`. |
| `POST /cases/{id}/review-decisions` | `{ "outcome": "Return" | "Close", "reasonOrResolution": "..." }`; `201 ReviewDecision` | Authorized Supervisor, case `AwaitingReview`. Return → `ReturnedForWork`; Close → `Closed`, records Supervisor/time/resolution. Required nonblank explanation. `If-Match`. |
| `POST /cases/{id}/reopen` | `{ "reason": "..." }`; `201 ReviewDecision` | Authorized Supervisor, `Closed` only. Preserve earlier closure, create reopen decision and transition to `InProgress` if active eligible assignee exists; otherwise `AwaitingAssignment`. `If-Match`. |

No general `PATCH /cases/{id}/status` lets a client bypass transitions. The returned-for-work case may be resumed by `POST /cases/{id}/resume-investigation` with an empty body and `If-Match`, moving `ReturnedForWork` → `InProgress` for the current eligible assignee. Mutations to notes, findings, links, or review-controlled case fields while `AwaitingReview` or `Closed` return `409 review_locked`/`invalid_transition`. Supervisor review must read permitted linked events, evidence, notes, findings, and activity before recording a disposition; the UI assembles these read routes.

**Priority** values `Low`, `Medium`, `High` are the MVP baseline represented in mockups; if the security/business design needs more, revise the data model and contract together. `dueAt` is a target, not a promise of automated escalation. `reviewCycle` identifies successive submissions after returns. The actor and decision timestamp are server-generated.

## 6. Evidence and file operations

| Method and path | Input/output | Guard and effect |
| --- | --- | --- |
| `POST /events/{id}/evidence` | Multipart `file` required, `classification?`, `description?`; `201 EvidenceMetadata` | Contributor on own draft before submission, or separately authorized actor in a permitted state. Blob staging and SQL finalization; only return `Available` after both succeed. Submitted-event correction is not a backdoor through this route. |
| `POST /cases/{id}/evidence` | Same; `201 EvidenceMetadata` | Permitted Investigator on editable case. A case view may also show attached files from its linked events without copying them. |
| `GET /events/{id}/evidence?cursor&pageSize` / `GET /cases/{id}/evidence?cursor&pageSize` | `200 EvidenceMetadata[]` pages | Apply parent record scope before metadata is disclosed. Exclude removed content from ordinary lists but retain history in audit/detail where authorized. |
| `GET /evidence/{id}` | `200 EvidenceMetadata` + ETag | Check associated event/case access; no public Blob path. |
| `GET /evidence/{id}/content` | `200` file stream | Check parent record and file access on each call; unavailable/removed → safe `404` or `409 file_unavailable` only when parent is visible. Audit access when security policy requires. |
| `PATCH /evidence/{id}` | `{ "classification?": "...", "description?": "...", "reason": "..." }`; `200 EvidenceMetadata` | Authorized metadata correction, editable parent state, `If-Match`; preserve prior metadata and audit. |
| `POST /evidence/{id}/remove` | `{ "reason": "..." }`; `200 EvidenceMetadata` (`Removed`) | Authorized removal, `If-Match`, preserve historical metadata/action. Does not promise physical deletion or disposal. |

Upload type/size checks, malware policy, and file-access logging are set by security design. File names are untrusted; enforce safe content disposition and do not allow direct Blob guessing. A failed Blob write does not leave an available file record. A missing Blob behind metadata is flagged `Unavailable`, emits telemetry, and returns an understandable error. File attachment on a follow-up response uses its multipart response operation above to keep the response and files associated.

The `POST /admin/service-identities` type and service permission codes are constrained by security design. A service identity shown for an Azure workload is still distinct from the platform-managed Azure managed identity credential. Admin routes never serve client secrets. `LastSignInAt` and `LastUsedAt` are best-effort informational values, never substitutes for security checks. User and service list pagination belongs inside the table card in the locked UI; that is a presentation concern.

**Configuration boundary:** The endpoint shapes exist so approved app-managed settings can be implemented; this document does **not** designate which keys exist or imply the final Configuration mockup is locked. Azure resource health may be offered later as read-only operational information if the deployment/observability design supports truthful status; no generic cloud-resource edit API exists here.

## 9. External ingestion and reprocessing

| Method and path | Input/output | Guard and effect |
| --- | --- | --- |
| `POST /integrations/events` | `IngestionEnvelope`; `202 IngestionOperation`, `Location: /api/v1/integrations/operations/{id}` | Approved active service identity with ingest capability. Validate envelope shape, bound payload, source/key; persist request + audit + outbox in one SQL transaction. No event success claim yet. Equivalent duplicate returns existing status (`202` if pending, `200` if terminal); conflicting payload/key → `409`. |
| `GET /integrations/operations/{id}` | `200 IngestionOperation` | Same owning service identity only (or separately authorized operator through admin path); no cross-source disclosure. |
| `POST /integrations/operations/{id}/corrections` | `{ "correctedEvent": { ... }, "reason": "..." }`; `201 CorrectionReference` | Original owning active service identity; failed/dead-lettered request only. `If-Match` on operation. Append corrected payload revision and audit; retain original hash/key; does not replay or create event by itself. Admin replay uses this revision. |

`IngestionEnvelope` has **required** `sourceSystem`, `sourceEventKey`, `event.title`, `event.description`, `event.occurredAt`, `event.sourceType`; optional approved `event.category`, `event.location`, and permitted attachment references if supported by the later upload/security policy. `sourceSystem` is bound to the service identity and cannot be impersonated by changing a string. The full envelope is stored privately and bounded; no arbitrary remote URL fetch or unauthenticated file ingestion is implied. Successful processing returns a created submitted event with `sourceSystem` and `ingestedAt`; invalid data returns a safe `failureCode` and no valid submitted event. The worker applies full validation, checks the source key again, writes the event, inbox receipt, outcome, and audit transactionally.

An invalid submission that fails **synchronous envelope validation** returns `422` and creates no operation. A syntactically valid accepted request can later fail deeper validation and retain a failed operation. Transport retries are at least once; inbox receipt and source key protect against duplicate business outcomes. A correction with the same external source key is an explicit revision of the existing failed request, not a new contradictory `POST /integrations/events`. The replay procedure does not expose full message bodies through an admin list or silently retry permanent failures.

Location: /api/v1/cases/31a2dc75-b6e3-4651-b452-68a98d21497e
ETag: "case-v1"
